# 2. Ограничения

Раздел фиксирует рамки, в которых принимаются архитектурные решения. Ограничения
снижают свободу проектирования, поэтому для каждого указано обоснование.
Источники: постановка задачи, условия АБС и почтового провайдера, формат учебного
проекта. Требования и цели качества приведены в разделе
[1-introduction-and-goals](1-introduction-and-goals.md).

## 2.1 Технические ограничения

| ID   | Ограничение                 | Описание                                                                                                                                                                                                                        | Обоснование                                                                        |
|------|-----------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------|
| TC-1 | Язык реализации             | Серверная логика, интеграции и тесты реализуются на Python.                                                                                                                                                                     | Требование учебного проекта, единый стек для всех сервисов.                        |
| TC-2 | Интеграция с АБС            | Получение портфеля должников и контактных данных по REST, формат JSON. Инициатор запроса: Система, метод выгрузки (pull). АБС не изменяется.                                                                                    | АБС предоставляет только REST API, push-уведомления и события недоступны.          |
| TC-3 | Почтовый провайдер          | Отправка электронной почты только через внешний публичный сервис (Яндекс.Почта или аналог). Прямая доставка получателям не используется. Провайдер возвращает коды ошибок, позволяющие отличить временный отказ от постоянного. | Требование заказчика, провайдер отвечает за репутацию и доставляемость писем.      |
| TC-4 | Лимит провайдера            | Система соблюдает настраиваемый лимит отправки. Целевое значение для учебного стенда: 10 писем в секунду. Фактическое значение уточняется по условиям провайдера, при меньшем лимите срок из QG-3 пересчитывается.              | Условие провайдера, превышение лимита ведёт к блокировке отправки.                 |
| TC-5 | Наблюдаемость               | Метрики, трейсы и логи экспортируются по OpenTelemetry Protocol (OTLP).                                                                                                                                                         | Требование эксплуатации, единый формат телеметрии.                                 |
| TC-6 | Объём рассылки              | Одна кампания содержит до 10 000 уникальных должников. В первой версии одному должнику соответствует одно сообщение электронной почты; при подключении новых каналов число сообщений оценивается отдельно.                      | Требование заказчика, определяет целевые показатели производительности.            |
| TC-7 | Журнал аудита               | Запись событий выполняется в режиме append-only. Изменение и удаление записей запрещены.                                                                                                                                        | Требование внутреннего аудита, сохранение доказательной базы.                      |
| TC-8 | Сетевой доступ              | АБС доступна из контура Системы по HTTPS, почтовый провайдер через интернет.                                                                                                                                                    | Существующая схема сети, Система не управляет внешними сегментами.                 |

## 2.2 Организационные ограничения

| ID   | Ограничение                  | Описание                                                                                                                             | Обоснование                                                                       |
|------|------------------------------|--------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------|
| OC-1 | Учебный проект               | Промышленная отказоустойчивость, резервирование, SLA и круглосуточная поддержка не требуются. Допускается один инстанс и перезапуск. | Цель проекта: демонстрация архитектурных практик, а не промышленная эксплуатация. |
| OC-2 | Аутентификация и авторизация | Вне объёма проекта. API считается доступным только из доверенного контура.                                                           | Учебное упрощение, не влияет на изучаемые архитектурные решения.                  |
| OC-3 | Интерфейс оператора          | Отсутствует в первой версии. Управление кампаниями выполняется через HTTP API.                                                     | Сокращение объёма, фокус на доменной логике и интеграциях.                        |
| OC-4 | Данные                       | Используются тестовые или обезличенные данные. Требования законодательства о персональных данных и банковской тайне не применяются.  | Учебный проект не работает с реальными данными клиентов.                          |
| OC-5 | Инфраструктура               | Один учебный стенд или локальная среда. Платные облачные сервисы и выделенный кластер не используются.                               | Ограничение бюджета и сложности учебного проекта.                                 |

## 2.3 Соглашения

| ID   | Соглашение   | Описание                                                                                          | Обоснование                                                    |
|------|--------------|---------------------------------------------------------------------------------------------------|----------------------------------------------------------------|
| CV-1 | Документация | Архитектура описывается в ARC42, диаграммы в C4, значимые решения в ADR. Язык документов русский. | Единая структура документации и прослеживаемость решений.      |
| CV-2 | Коммиты      | Используются Conventional Commits на русском языке.                                               | Единообразие истории и контроль изменений.                     |
| CV-3 | Ветвление    | Изменения кода выполняются в отдельной feature-ветке.                                             | Изоляция незавершённых изменений и упрощение ревью.            |
| CV-4 | Конфигурация | Параметры задаются переменными окружения. Секреты и учётные данные не хранятся в репозитории.     | Безопасность и переносимость между средами.                    |
| CV-5 | Логирование  | Логи структурированные, без полных персональных данных. Адрес электронной почты маскируется.      | Диагностика без раскрытия чувствительных данных.               |
| CV-6 | Язык кода    | Идентификаторы, имена API и схем БД на английском. Комментарии и документация на русском.         | Совместимость с экосистемой Python и единый язык документации. |
| CV-7 | Инкрементальная разработка | Разработка ведётся этапами. Первый этап создаёт инфраструктуру, телеметрию и Docker Compose, при которых сервис полностью запускается и проходит health без бизнес-функционала. Каждый следующий этап добавляет один законченный инкремент функционала сквозь все слои и не ломает сборку, миграции, health и запуск в Compose. | Ранняя проверка интеграций и инфраструктуры, постоянный рабочий стенд и снижение риска поздних проблем. |

Инкремент считается завершённым, когда он проходит сквозной путь от API или очереди до хранения, покрыт тестами и оставляет `make up-all`, `make migrate` и `make check` в рабочем состоянии. Промежуточный этап не оставляет сервис в нерабочем состоянии и не требует ручных шагов, кроме описанных в README.

# 4. Стратегия решения

Раздел фиксирует фундаментальные решения, которые определяют архитектуру
LoanDebtors: технологии, верхнеуровневую декомпозицию, способы достижения целей
качества и организационные рамки. Основание: разделы
[1-introduction-and-goals](1-introduction-and-goals.md),
[2-constraints](2-constraints.md) и
[3-context-and-scope](3-context-and-scope.md). Детализация строительных блоков
и интерфейсов выполняется в разделе 5.

## 4.1 Технологические решения

| Решение                                      | Обоснование                                                                                                                                                      |
|----------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Python 3.12+, FastAPI и Pydantic v2          | Язык зафиксирован в TC-1. FastAPI даёт REST API, OpenAPI и асинхронную работу с АБС, SMTP и RabbitMQ. Pydantic используется для валидации контрактов и настроек. |
| PostgreSQL, SQLAlchemy 2 и Alembic           | Общая СУБД с отдельными схемами, транзакционный outbox, append-only аудит. SQLAlchemy отвечает за доступ к данным, Alembic за миграции каждого сервиса.          |
| RabbitMQ и aio-pika                          | Очередь по заданию. Durable-очереди, publisher confirms, manual ack, DLX и retry-очереди обеспечивают надёжную асинхронную доставку и развязку сервисов.         |
| APScheduler                                  | Планирование запуска кампаний по расписанию. MemoryJobStore, cron и one-off задания, misfire и coalesce; источник истины `CampaignSchedule` в PostgreSQL, задания восстанавливаются при старте. |
| OpenAPI 3.1 и AsyncAPI 3.0                   | Контракты REST и сообщений RabbitMQ создаются до реализации, версионируются и проверяются контрактными тестами. Это основа API-first.                            |
| OpenTelemetry SDK и OTLP                     | Метрики, трейсы и логи по TC-5. `TracerProvider`, `MeterProvider` и `LoggerProvider` экспортируют данные по OTLP в OTel Collector; на стенде Collector передаёт трейсы в Tempo, метрики в Prometheus, логи в Loki, а Grafana показывает все виды данных. Trace context передаётся через HTTP и RabbitMQ, что связывает вызов АБС, обработку сообщения и ответ провайдера. |
| Grafana Loki                                 | Централизованное хранение и поиск логов, LogQL, связь лога с трейсом по `trace_id`. Retention и метки OTLP настраиваются в конфигурации Loki. |
| pytest, pytest-bdd, Testcontainers и Mailpit | Модульные и BDD-тесты, интеграционные тесты с реальными PostgreSQL и RabbitMQ, локальный SMTP-сервер без внешней сети.                                           |
| Punq                                         | Удобный IoC-контейнер для соответствия принципам SOLID.                                                                                                          |
| Jinja2                                       | Шаблоны канальных сервисов, в первой версии email. Рендеринг выполняется в канальном сервисе по F-03.                                                            |
| Ruff и mypy                                  | Единый стиль, статическая проверка типов и раннее обнаружение ошибок в CI.                                                                                       |
| Docker Compose                               | Один учебный стенд с PostgreSQL, RabbitMQ, OTel collector, Tempo, Prometheus, Grafana, Mailpit и сервисами. Без Kubernetes и платных облачных ресурсов по OC-5. |

**Телеметрия и Мониторинг.**

Сервисы используют три SDK-провайдера OpenTelemetry: `TracerProvider` для
трейсов, `MeterProvider` для метрик и `LoggerProvider` для логов. Логи
одновременно пишутся структурированным JSON в stdout по CV-5 и отправляются по
OTLP. Все провайдеры экспортируют данные в OTel Collector. Коллектор является
единственной точкой интеграции с системой Мониторинга: на учебном стенде он
передаёт трейсы в Grafana Tempo, отдаёт метрики для Prometheus, отправляет
логи в Grafana Loki, а Grafana показывает трейсы, метрики, логи и дашборды.

Выбор провайдеров, атрибуты ресурсов, сэмплирование, логи и передача контекста
описаны в разделе [8-cross-cutting-concepts](8-cross-cutting-concepts.md),
размещение компонентов стенда в разделе
[7-deployment-view](7-deployment-view.md).

### 4.1.1 Архитектурные принципы

| Принцип                | Применение                                                                                                                                                                                                                                                                                    |
|------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Hexagonal Architecture | Каждый сервис делится на слои `domain`, `application`, `ports`, `adapters`, `infrastructure`. Домен не зависит от FastAPI, SQLAlchemy и aio-pika. Порты описывают репозитории, очередь, отправку email, аудит и телеметрию, адаптеры реализуют их для PostgreSQL, RabbitMQ, SMTP, АБС и OTel. |
| API-first              | Контракты OpenAPI и AsyncAPI являются источником истины. Реализация проходит контрактные тесты, а изменения контрактов версионируются.                                                                                                                                                        |
| TDD/BDD                | Новый функционал начинается с теста. Бизнес-правила проверяются модульными тестами, ключевые потоки описываются Gherkin-сценариями, внешние зависимости заменяются тестовыми адаптерами.                                                                                                      |
| SOLID                  | Сервисы и модули имеют одну причину для изменения. Новые каналы добавляются без изменения доменного ядра. Порты разделены по назначению, зависимости направлены к домену.                                                                                                                     |
| Микросервисы           | Границы проходят по бизнес-возможностям. Каждый сервис является отдельной единицей развёртывания, владеет своей схемой БД и общается с другими через REST или события.                                                                                                                        |

## 4.2 Принципы реализации

**Данные.**

Используется один физический инстанс PostgreSQL. Каждый сервис владеет своей
схемой, своими миграциями и таблицей outbox. Прямые запросы в чужие схемы запрещены.
Общая СУБД является учебным упрощением, границы сервисов сохраняются за счёт 
владения схемами и обмена через API и события.

**Межсервисные взаимодействия.** 

Синхронные команды и чтение выполняются через REST.
Выполнение кампании и доставка идут через RabbitMQ. 
В очередь передаётся канально-нейтральная команда с `template_key` и переменными, а рендеринг выполняет канальный сервис.
Используются: 
- durable-очереди, 
- publisher confirms, 
- manual ack, 
- prefetch,
- retry-очереди с TTL и 
- DLQ. 

Гарантия доставки at-least-once, дедупликация по `message_id`, публикация событий через транзакционный outbox. 
Trace context передаётся в HTTP-заголовках и заголовках сообщений RabbitMQ. Аудит пишется асинхронно: сервис синхронно фиксирует `audit.event` в outbox своей схемы, `Audit Exporter` потребляет событие из очереди и пишет append-only журнал в схему `audit`.

**Общая логика канальных адаптеров.**

В текущей реализации отдельный класс `BaseChannelAdapter` не выделен. Email
Channel содержит общую логику канального сервиса:
- приём `NotificationCommand` и проверка идемпотентности по `message_id`;
- вызов рендеринга и отправки;
- классификация ошибок провайдера на временные и постоянные;
- публикация `message.sent` и `message.failed`;
- запись audit-событий в outbox;
- метрики, трейсы и trace context;
- проверка конфигурации и health.

Различия канала сосредоточены в рендеринге, отправке, классификации ошибок,
проверке конфигурации и политике rate limit. Новый канал добавляется отдельным
channel-сервисом с тем же контрактом; выделение общего базового класса остается
точкой расширения.

**Границы и допущения.**

- API gateway и CLI не выделяются. Управление выполняется через HTTP API сервисов.
- На учебном стенде запускается один экземпляр каждого сервиса, один RabbitMQ и один PostgreSQL. 
Горизонтальное масштабирование допускается, но не требуется.
- Запуск кампании требует полной выгрузки выборки из АБС. При недоступности АБС кампания не запускается, 
частичная выборка не допускается.
- Новый канал SMS или мессенджера добавляется отдельным channel-сервисом с тем же контрактом, 
без изменений доменного ядра.

## 4.3 Достижение целей качества

| Цель качества                     | Подход / стратегия                                                                                                                                                                                                                            |
|-----------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| QG-1 Расширяемость каналов        | Hexagonal Architecture, общий порт отправки сообщения и отдельный channel-сервис для каждого канала. Новый адаптер не меняет домен и существующие тесты.                                                                                      |
| QG-2 Тестируемость и корректность | Тестовая пирамида: модульные тесты на pytest, Gherkin-сценарии на pytest-bdd, контрактные тесты, интеграционные тесты с Testcontainers и Mailpit. Внешние зависимости заменяются тестовыми адаптерами.                                        |
| QG-3 Пропускная способность       | Кампания на 10 000 должников. Глобальный rate limiter с целевыми 10 письмами в секунду.                                                                                                                                                       |
| QG-4 Наблюдаемость                | OTel SDK в каждом сервисе, trace context в HTTP и RabbitMQ, метрики по кампаниям, сообщениям, попыткам, ретраям, глубине очереди и задержкам, структурированные логи с `trace_id` и `span_id`. Логи хранятся в Loki, метрики и трейсы в Prometheus и Tempo. Append-only аудит (TC-7) пишется через outbox. |
| QG-5 Надёжность доставки          | Durable-очереди, publisher confirms, manual ack, ключ идемпотентности `message_id`, retry с backoff, DLQ, outbox и хранение состояния кампании в PostgreSQL. После перезапуска обработка продолжается с последнего подтверждённого сообщения. |

## 4.4 Организационные решения

- Монорепозиторий: `source/services/<service>`, `source/contracts`, `source/infra`. Контракты хранятся отдельно от реализаций.
- Contract-first: OpenAPI и AsyncAPI проходят ревью до реализации, контрактные тесты входят в CI.
- ADR для значимых решений: RabbitMQ, общая СУБД, границы сервисов, outbox, API-first. Каталог ADR в разделе 9-architectural-decisions.
- Локальный запуск через Docker Compose: PostgreSQL, RabbitMQ, OTel collector, Mailpit и четыре сервиса.
- Аутентификация и авторизация не реализуются по OC-2. Секреты передаются через переменные окружения.
- Минимальная инфраструктура: один PostgreSQL, один RabbitMQ, один OTel collector, Mailpit.

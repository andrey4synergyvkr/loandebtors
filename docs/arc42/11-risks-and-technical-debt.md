# 11. Risks and Technical Debt

Раздел фиксирует известные риски и технический долг: описание, оценку
вероятности и влияния, меры реагирования.

## 11.1 Risks

| Риск | Описание | Вероятность / влияние | Меры реагирования |
|------|----------|-----------------------|-------------------|
| R-01 Ошибки SMTP-провайдера | Провайдер отвечает 4xx/5xx, ограничивает скорость или блокирует отправителя | Средняя / Среднее | Классификация ошибок, retry через Notifications по `retryable`, rate limiter, health и метрики |
| R-02 Повторная отправка письма | Сбой между ответом SMTP и записью результата приводит к повторной отправке при at-least-once | Средняя / Среднее | Идемпотентность по `message_id`, `send_attempts`, ограничение `max_attempts`, фиксация в README |
| R-03 Нестабильный Docker Engine на стенде | Интеграционные тесты и контейнеры недоступны, проверки пропускаются | Средняя / Среднее | `INTEGRATION_REQUIRED=1` в CI, e2e-job на Compose, перезапуск Docker Desktop при сбое |
| R-04 Зависание АБС | Заглушка или внешняя АБС принимает соединение, но не отвечает, consumer долго ждет таймаут | Средняя / Среднее | Таймауты, ограниченный retry, health и алерты по длительности |
| R-05 Рост outbox и аудита | Кампания на 10 000 должников создает 10 000 `message.send` и 10 000 `message.queued` audit-событий | Высокая / Среднее | Retention outbox и попыток, батчи, решение об агрегировании `message.queued` |
| R-06 Зависший `campaign.start` | Исчерпание retry или сбой consumer оставляет кампанию в `running` | Низкая / Высокое | Maintenance worker повторно ставит `campaign.start`, проверка `maintenance` в health |
| R-07 Нет аутентификации API | Любой клиент доверенного контура может управлять кампаниями | Низкая / Среднее | Принято ограничением OC-2, доступ только из доверенного контура |

## 11.2 Technical Debt

| Долг | Описание | Причина возникновения | План устранения |
|------|----------|-----------------------|-----------------|
| TD-01 Дублирование consumer | `NotificationCommandConsumer` и `NotificationResultConsumer` почти полностью повторяют друг друга | Быстрое добавление второго consumer | Вынести общий базовый класс или композицию supervisor, retry и DLQ |
| TD-02 Нет API истории попыток | Таблица `message_attempts` есть, но оператору не отдается | В OpenAPI нет отдельного маршрута | Добавить endpoint при необходимости или включить attempts в ответ сообщения |
| TD-03 Retention только для outbox и попыток | Снимки и сообщения завершенных кампаний не удаляются | Осторожность с доменными данными | Добавить политику архивации и удаления по завершенным кампаниям |
| TD-04 `message.queued` на каждое сообщение | Аудит растет линейно от числа должников | Требование QG-4 | Решить, нужно ли агрегировать событие по кампании |
| TD-05 Maintenance по умолчанию раз в час | Зависшие кампании восстанавливаются с задержкой до часа | Консервативный интервал | Уменьшить интервал или запускать проверку при старте |
| TD-06 Ручной разбор DLQ | Redrive DLQ реализован скриптом, автоматического разбора нет | Учебный стенд | Добавить runbook и автоматический redrive при необходимости |

Закрытые пункты: контрактный тест DLQ покрыт проверками
`decode_for_dead_letter` и messaging-контракта, пропуск интеграционных тестов
в CI запрещен переменной `INTEGRATION_REQUIRED=1`.

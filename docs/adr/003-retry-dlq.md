# ADR-003: Retry-очереди и DLQ

## Контекст

Временные ошибки RabbitMQ, АБС и внешнего провайдера не должны терять сообщения
и не должны блокировать очередь. Постоянные ошибки валидации не имеют смысла
для повтора.

## Решение

Для каждой основной очереди объявляются retry-очередь с TTL и dead-letter
очередь. Consumer использует manual ack:

- временная ошибка: `nack(requeue=False)`, сообщение уходит в retry-очередь;
- исчерпание `rabbitmq_retry_max_attempts`: публикация в DLQ и ack;
- ошибка валидации: публикация в DLQ и ack.

После истечения TTL RabbitMQ возвращает сообщение в основную очередь с routing
key очереди, а не с исходным routing key. Consumer принимает ключ очереди и
определяет тип по телу либо по допустимому набору routing keys.

## Последствия

- Очередь не блокируется «ядовитым» сообщением.
- Повторы ограничены и наблюдаемы.
- Consumer должен быть устойчив к потере исходного routing key.
- Scheduler принимает ключ `scheduler.commands` и определяет тип события по
  наличию поля `schedule` в теле. Notifications использует тот же прием для
  `notification.commands` и `notification.results`.
- Для каждого consumer счетчик `x-death` считается по своей retry-очереди,
  поэтому исчерпание повторов не зависит от соседних очередей.

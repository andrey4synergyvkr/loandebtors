# ADR-001: Транзакционный outbox

## Контекст

Notifications изменяет состояние кампании и должно публиковать события в
RabbitMQ. Прямая публикация из обработчика HTTP создает окно между коммитом
PostgreSQL и публикацией: при сбое процесс может зафиксировать состояние, но не
опубликовать событие, или наоборот.

## Решение

Все исходящие события и команды пишутся в таблицу `notification.outbox` в той же
транзакции, что и состояние. Фоновый outbox relay выбирает готовые записи через
`FOR UPDATE SKIP LOCKED`, публикует их с publisher confirms и фиксирует
`published_at`. При ошибке запись остается в outbox с увеличенным `attempts`,
`last_error` и новым `available_at`.

Отложенные публикации используются для повторов сообщений: `available_at`
равен `next_attempt_at`.

## Последствия

- Гарантия at-least-once для событий и команд.
- Потребители обязаны быть идемпотентными.
- Outbox растет, нужна политика retention.
- Публикация становится асинхронной, HTTP-ответ не ждет RabbitMQ.
